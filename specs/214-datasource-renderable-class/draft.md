# Draft: 214-datasource-renderable-class

**開発種別:** refactor
**目的:** DataSource メソッドの戻り値を構造化された値型に昇格させ、OOP による型システムで出力構造を表現する。

## Requirements

優先度順:

1. **[必須] 構造化された戻り値型の導入** — When DataSource の resolver メソッドが呼び出されたとき、戻り値は出力構造を表現する値型または null でなければならない。文字列 Markdown 断片の直接返却は許容されない。
2. **[必須] 構築時 invariant の強制** — When 戻り値型が構築されるとき、意味的に不整合な状態（例: 内部データの形状不一致）は構築時点で例外にならなければならない。
3. **[必須] 展開層のポリモルフィック化** — When `{{data: ...}}` ディレクティブが展開されるとき、展開層は戻り値型に対して統一インターフェースを呼び出し、具体型に依存した分岐を行ってはならない。
4. **[必須] 既存 DataSource の一貫した移行** — If 既存の DataSource メソッドが文字列を返している場合、新しい戻り値型に移行されなければならない。移行後は文字列返却サポートが残存してはならない。
5. **[必須] 出力互換性** — When 移行が完了したとき、docs の最終 Markdown 出力は移行前と同一でなければならない。
6. **[重要] Markdown 主要構成要素の網羅** — When 型システムが提供されるとき、Markdown の主要ブロック構成要素（表・箇条書き・番号付きリスト・段落・コードブロック・引用・見出し・連結）のそれぞれに対応する具象型が 1 対 1 で定義されていなければならない。具象型の個数は 8 であり、それぞれが当該 Markdown 構成要素を出力するメソッドを持つ。
7. **[重要] 外部 preset からの公開** — When 外部 preset のコードが本値型を import するとき、sdd-forge の公開エクスポート経路（`container` 経由または明示エクスポート）から直接解決可能でなければならない。内部パスへの直接依存を要求してはならない。
8. **[重要] 出力形式拡張に対するオープン性** — When 将来 Markdown 以外の出力形式を追加するとき、既存の値型の実装・インターフェース契約を変更することなく、新しい出力メソッドを追加する形で対応できなければならない（Open/Closed 原則）。既存コード（DataSource・展開層）の改修を必要としてはならない。

## Scope Verification
- In scope:
  - 構造化戻り値型（型システム）の導入
  - 既存の全 DataSource メソッドの新型への移行
  - 展開層の新型対応
  - 移行後の文字列返却サポートの削除
- Out of scope:
  - Markdown 以外の出力形式（HTML 等）の実装
  - プロジェクト設計方針文書（CLAUDE.md / AGENTS.md 等）への追記
  - analysis.json / overrides.json のスキーマ変更
  - CLI サブコマンドの変更

## Impact on Existing Features
- 影響ありの既存機能:
  - `{{data: ...}}` ディレクティブの展開層: resolver 戻り値の型が変更される
  - 全 DataSource メソッド: 戻り値型が変更される（破壊的変更、alpha 期間のため許容）
  - 外部 preset（npm 配布利用側）の自作 DataSource: 新型への移行が必要（破壊的変更）
- 影響なし:
  - `analysis.json` の生成（scan / enrich フェーズ）
  - docs の最終 Markdown 出力（バイト列は不変であることを要件 5 で保証）
  - CLI サブコマンド体系

## Q&A
- Q: スコープは部分移行とフル移行のどちらか？
  - A: フル移行（文字列返却サポートを削除）。
  - 根拠: (1) alpha 版ポリシー（CLAUDE.md）により「後方互換コードは書かない」方針。部分移行は文字列／新型両対応の展開層ロジックを恒久化するため妥当でない。

- Q: 戻り値型の表現粒度（最小 2 種類か、細分化か）？
  - A: Markdown の主要ブロック構成要素を網羅する粒度。
  - 根拠: (1) ユーザー判断 — 型システムは選択肢の完備性が作者の表現力に直結する。(2) 画像・リンク・水平線は段落内の Markdown 記法で十分表現できるため値型化から除外（YAGNI との整合）。

- Q: 移行のコミット／PR 戦略は？
  - A: spec フェーズの task 分解機能に委ねる。
  - 根拠: (3) 既存コードパターン — sdd-forge の spec 機能は task 分解をサポートしており、粒度判断を spec フェーズに委ねるのが一貫した設計。

- Q: 出力互換性はどう検証するか？
  - A: 既存 DataSource に対するスナップショット比較で保証する。詳細は spec フェーズでテスト設計に展開。
  - 根拠: (3) 既存コードパターン — docs 出力のリグレッション検知はスナップショット比較が既存 preset テストで採用されている手法。

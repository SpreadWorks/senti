## Summary

Align the impl-review prompt with the output parser/schema contract. When returning review findings, each finding must include a valid `requirementId` required by the parser. Schema validation failures must not be treated as semantic review results. If no valid output can be obtained after exhausting provider internal retries and flow-side tooling retries, the flow must stop with a clear tooling failure that identifies the cause.

After the fix, the Issue #436 flow should be rebased onto the fixed base and be resumable from a normal next-action without special state repair or counter manipulation.

## Background

- Issue #436 runId `59054765-3b3a-4151-8a0b-96762c91bfba` stopped twice in a row at impl-review.
- In each run, after 3 provider internal retries, the provider returned 40 or 41 `nonBlockingImprovements`.
- None of the returned findings had the parser-required `requirementId`, so schema validation failed.
- No semantic verdict was generated, and the flow's `reviewRetry` was not consumed. This is not a semantic review failure; it is a prompt/output contract or tooling protocol failure.
- A `Preset not found: node-cli` warning was recorded once, but it is not the main cause of this schema validation failure.

## Problem

The impl-review generation instructions and the consumer-side schema contract are inconsistent, so even if the model follows the prompt and returns findings, the parser cannot accept them. Currently, the same invalid shape is repeated after internal retries, and the flow stops without being able to generate a semantic verdict.

If this boundary remains ambiguous, schema/tooling failures and semantic review results become mixed together, breaking the meaning of `reviewRetry`, state promotion, and review artifacts. When the contract is not satisfied, the result must not be normalized as a semantic PASS/FAIL or improvement finding; it must be handled consistently as a tooling failure.

## Acceptance Criteria

- The impl-review prompt/output contract explicitly requires a valid `requirementId` for every requirement-scoped finding, including both blocking and non-blocking findings.
- Valid findings generated by impl-review have a requirement ID that exists in the target spec and pass parser/schema validation.
- If review observations not tied to a requirement must be allowed, their representation is defined uniquely in both the prompt and schema. Do not make it optional on only one side and leave the inconsistency in place.
- Missing required fields, unknown requirement IDs, and other output schema violations do not generate a semantic verdict.
- Schema/tooling failures do not consume `reviewRetry` and are not recorded as semantic findings, semantic FAILs, deferred findings, or artifacts.
- Provider internal retries and flow-side tooling retries are bounded according to the existing policy. After the limit is reached, return a clear tooling failure that identifies the failure class, target review, validation error, and attempt information. Do not cause infinite retries or silent loops of the same next-action.
- Preserve existing behavior for normal impl-review PASS/FAIL, semantic retries, counter updates, state promotion, and artifact generation.
- Do not change existing behavior for prompts, schemas, counters, state, or artifacts of other review types such as draft/spec/test/acceptance. However, minimal commonization is allowed if necessary to reuse an existing shared contract and resolve the impl-review inconsistency.
- The `Preset not found: node-cli` warning is not part of this issue's fix and must not be treated as the cause of the impl-review schema failure.
- After rebasing Issue #436 onto the fixed base and running a normal next-action, impl-review can be retried without manual counter/state/artifact rewriting.

# Draft: test-first determinism core

**開発種別:** 機能追加 (ENHANCE) — cac6/T4 Phase 2 本体実装

**目的:** cac6/T4 Phase 1 (#185) で確立した step 構造・phase 割当の骨格の上に、test-first 決定論化の振る舞いを載せる。具体的には (1) テスト実行を AI から切り離した確定的ツール、(2) テスト記述段階での実装差分への hard wall、(3) 追加タスクの自律 draft 生成、(4) 統合 step の skip 初期化。

**検討モード:** 以下の Requirements / Q&A は、Q1-Q6 で利用者と合意に至った「決定事項」として記述する。ブレーンストーミング中の試案ではない。

## Requirements

要件は優先度順に並ぶ (P1 が最優先)。

### P1 — REQ-2: テスト実行の確定化

- **When** 利用者が何らかのスコープでテスト実行を要求したとき、**shall** ツールが対応するテストコマンドを決定して子プロセスとして起動し、結果を保存する。
- **When** 現在対象のタスクが存在する場合、**shall** タスク単位のスコープとして解釈する。**If** 対象タスクが無い場合は親レベルのスコープとする。
- **When** プロジェクトがテストコマンドを明示的に設定している場合、**shall** その設定を採用する。**If** 未指定なら利用可能なテストスクリプトから推論する。
- **When** テスト実行が完了したとき、**shall** 終了コードとテスト種別ごとの件数サマリを flow 状態に記録する。
- **When** AI プロセスがテスト結果値の書き込みを試みても、**shall** ツールがその書き込み経路を独占し、AI 側からは書き換えられないようにする。

### P2 — REQ-3: テスト記述段階の実装差分 hard wall

- **When** flow がテスト記述段階にある間、**shall** 該当 spec が宣言する実装対象ファイルへの context アクセス要求を拒否する。
- **When** 実装対象ファイルを列挙する必要がある場合、**shall** spec の構造化データの中で表現可能とする。
- **When** 実装対象へのパス指定 context 取得が要求されたとき、**shall** エラーを返して取得させない。
- **When** 一覧・検索型の context 取得が要求されたとき、**shall** 実装対象に該当するエントリーを結果から除外する。
- **When** テスト記述段階で使われる skill/プロンプト、**shall** 「実装差分を参照しない」方針を文書化する (ツール側 hard wall の補強として)。

### P3 — REQ-7: 追加タスク origin の自律 draft 生成

- **When** 追加タスクが挿入されたとき、**shall** ツールが親 spec・既存タスク群・上位要求文書を context として AI 呼び出しで draft を生成する。
- **When** 生成された draft が gate に掛けられたとき、**shall** gate の判定のみを信頼点として採用し、AI 自己判断での承認/却下を行わない。
- **When** gate が FAIL したとき、**shall** 既存 flow の retry 上限と同値のリトライを行う。**If** 上限に達した場合は利用者に escalate する。
- **When** 自動承認モードが有効で gate が PASS したとき、**shall** 追加タスクの draft を自動承認して次段階へ進む。
- **When** skill レイヤから追加タスク draft が要求されたとき、**shall** 上記ツール経路を必ず経由し、skill 内で AI が独自に draft を生成しないようにする。

### P4 — 統合 step の skip 初期化

- **When** 新規 flow を初期化する時点で、**If** spec が tasks を持たない場合、**shall** 統合系 step を `skipped` 状態で登録する。
- **If** 既存の pending 状態が残っている既存 flow がある場合、**shall** マイグレーションは行わない。
- **When** skill 側が step 状態から次アクションを判定するとき、**shall** `skipped` 状態の統合 step を処理対象から除外し、次の非 skipped step に遷移する。

## Impact on existing features

- **既存 flow 状態**: tasks を持たない既存 flow では統合 step が pending のまま残るが、skill 側で未参照のため実害なし。新規 flow のみ影響を受ける。
- **プロジェクト設定スキーマ**: テストコマンド設定が追加されるが、省略可能。未指定時は従来通り既存スクリプトからの推論に退化する。
- **spec 構造化データ**: 実装対象を表すフィールドが 1 つ追加される。省略時は hard wall が無効化され従来挙動となる。
- **context 取得 API**: テスト記述段階でのみ除外が適用される。他 phase の挙動は変わらない。
- **skill テンプレート**: テスト記述段階の方針明文化と追加タスク経路の書き換えを伴い、配布メカニズム経由でユーザーに届く。

## Constraints

- 外部依存なし (組み込みモジュールのみ)。
- AI 呼び出しは既存のエージェント呼び出しパターンを踏襲する。
- 後方互換シム不可 (alpha 方針)。
- 配布コード配下にプロジェクト固有情報を書かない。
- コミットメッセージは英語で書く。

## Edge cases

- テストコマンド設定が不完全な場合: 設定検証で reject する。
- テストスクリプトが存在しない場合: 明示エラーで停止し、黙ったフォールバックは行わない。
- テスト結果の件数抽出に失敗した場合: 終了コードのみ記録し、件数は部分記録として警告を出す。
- 実装対象宣言が空の場合: hard wall は無効 (従来挙動)。
- 追加タスク draft 生成の retry 途中でユーザー割り込みがあった場合: エラーを返し、issue-log に記録して再開可能にする。

## Test strategy

- **恒久回帰テスト** (プロジェクト共通のテスト配置場所):
  - テスト実行ツールの起動・exit code 伝搬・サマリ記録・設定優先順位
  - テストコマンド設定のスキーマ検証 (OK/NG)
  - 初期 step 構築における tasks 有無の分岐
  - context 除外フィルタのパス判定
  - 追加タスク draft 生成の AI 呼び出し + gate + retry 上限の振る舞い
- **spec 固有シナリオ** (spec 直下のテスト配置):
  - 1 タスクを完走させて step 順序と親サマリ合算を end-to-end で検証
  - 検証内容と実行方法を記した README

## Alternatives considered

- テスト実行を AI 自己申告で完結: 決定論が崩れるため却下 (Issue の主要動機)。
- 実装対象 glob を spec.md に記述: 構造的検証ができず、進行中の spec 構造化方針に反するため却下。
- 追加タスク draft 生成を skill 改変のみで実現: retry/escalate の一貫性が AI 判断依存になり、「gate のみが信頼点」を満たせないため却下。
- 統合 step の既存 flow 遡及適用: alpha 方針 (後方互換シム禁止) に反するため却下。

## Future extensibility

- テスト実行ログの件数解析を preset 別に拡張可能。初期版は汎用的に扱い、後付けで preset 固有の parser を差し込める構造とする。
- 実装対象宣言は将来、spec からの差分推定で自動算出する余地がある。
- 追加タスク用の draft 生成ツールは将来 plan origin の draft 自動生成にも流用できる。

## Q&A

- **Q1:** Issue の解釈確認 (REQ-2/REQ-3/REQ-7 + 統合 step skip 初期化)
  - **推奨:** Issue 本文の 4 スコープをそのまま採用し、追加スコープを入れない。
  - **根拠:** (1) Issue 本文のスコープ列挙、(2) 「スコープを勝手に narrow しない」という Issue 経緯セクションの指摘。
  - **A:** [1] 承認
- **Q2:** テスト実行コマンドの設定配置
  - **推奨:** top-level `commands` 配下に配置。省略時はスクリプト推論。
  - **根拠:** (1) Issue 本文の literal 記述、(2) 既存コードパターン (他の top-level ツール設定との揃え)、(3) alpha 方針 (単一構造に絞る)。
  - **A:** [1] 承認
- **Q3:** 実装対象 glob の配置先
  - **推奨:** spec 構造化データのみ。プロジェクト設定への配置は不採用。
  - **根拠:** (1) ユーザー指摘「プロジェクト全体設定に書く意味がない」、(2) 実装対象は spec ごとに完全に異なる、(3) 進行中の spec 構造化方針。
  - **A:** [2] 採択 (プロジェクト設定配置は却下)
- **Q4:** 追加タスク自律 draft 生成の実装層
  - **推奨:** ツール主導。skill 任せにしない。
  - **根拠:** (1) Issue 本文「gate のみが信頼点」「retry 上限同値で escalate」、(2) 既存のツール主導 gate/review パターン、(3) skill 任せは AI 判断ブレによる早期 escalate リスク。
  - **A:** [1] 承認
- **Q5:** 統合 step skip 初期化の適用範囲
  - **推奨:** 新規 flow のみ。マイグレーションなし。
  - **根拠:** (1) プロジェクト規約の alpha 方針、(2) 既存 active flow は自己完結で影響小、(3) 既存 pending の残留は実害なし (skill 側未参照)。
  - **A:** [1] 承認
- **Q6:** テスト配置
  - **推奨:** 恒久価値あるものは共通配置、spec 固有シナリオは spec 配下。
  - **根拠:** (1) 判断基準「壊れたら常にバグか？」、(2) 既存のテスト配置慣習。
  - **A:** [3] 承認

# Test Design

### Test Design

- **TC-1: Failure taxonomy definitions exist**
  - Type: unit
  - Input: Inspect exported code constants/classes or CLI-facing docs.
  - Expected: Taxonomy distinguishes at least `review verdict failure`, `subprocess failure`, `provider failure`, `input size failure`, and `maxAttempts exceeded`.

- **TC-2: Mechanical subprocess retry uses taxonomy**
  - Type: unit
  - Input: Simulate subprocess failures classified as retryable and non-retryable.
  - Expected: Retry decision is derived from taxonomy classification, not ad hoc string matching.

- **TC-3: Retryable subprocess failure retries up to existing default**
  - Type: integration
  - Input: `run-review` subprocess exits with retryable subprocess failure twice, then succeeds.
  - Expected: Command retries mechanically and succeeds; total subprocess attempts do not exceed 3.

- **TC-4: Retryable subprocess failure stops after max 3 attempts**
  - Type: integration
  - Input: `run-review` subprocess always fails with retryable subprocess failure.
  - Expected: Exactly 3 subprocess attempts occur; failure envelope reports final failure without a fourth attempt.

- **TC-5: Signal termination is not retried**
  - Type: integration
  - Input: Subprocess terminates by signal.
  - Expected: No retry occurs; failure is classified as non-retryable subprocess failure.

- **TC-6: Killed subprocess is not retried**
  - Type: integration
  - Input: Subprocess result has `killed=true`.
  - Expected: No retry occurs; failure is classified as non-retryable subprocess failure.

- **TC-7: Input size failure is not retried mechanically**
  - Type: integration
  - Input: `run-review` receives machine-readable marker with `classification=input size failure`.
  - Expected: No subprocess retry occurs; `reviewRetry` budget is not consumed.

- **TC-8: Provider failure does not consume reviewRetry**
  - Type: integration
  - Input: `review.js` detects provider failure and emits machine-readable marker.
  - Expected: `flow.json reviewStop` or envelope data includes `classification`, `reason`, `retryBudgetConsumed=false`, `recoveryHint`, and `recoveryCommand`.

- **TC-9: Input size failure does not consume reviewRetry**
  - Type: integration
  - Input: `review.js` detects input size failure and emits machine-readable marker.
  - Expected: `flow.json reviewStop` or envelope data includes `classification`, `reason`, `retryBudgetConsumed=false`, `recoveryHint`, and `recoveryCommand`.

- **TC-10: Review verdict failure consumes reviewRetry when applicable**
  - Type: integration
  - Input: Review completes normally and returns a failing verdict.
  - Expected: Failure is classified as review verdict failure; retry handling follows reviewRetry policy and differs from provider/input size failures.

- **TC-11: Max attempts exceeded envelope preserves existing fields**
  - Type: unit
  - Input: Trigger `REVIEW_MAX_ATTEMPTS_EXCEEDED`.
  - Expected: Envelope data includes existing `phase`, `attempts`, `max`, plus `recoveryCommand`.

- **TC-12: Max attempts exceeded boundary**
  - Type: integration
  - Input: Review reaches exactly configured maximum attempts.
  - Expected: No extra review attempt is started; `REVIEW_MAX_ATTEMPTS_EXCEEDED` is emitted with correct `attempts` and `max`.

- **TC-13: Machine-readable stderr marker format**
  - Type: unit
  - Input: Provider failure and input size failure generated by `src/flow/commands/review.js`.
  - Expected: Exactly one parseable stderr marker line is emitted containing `classification`, `reason`, `recoveryHint`, and `recoveryCommand`.

- **TC-14: Marker parsing tolerates normal stderr noise**
  - Type: unit
  - Input: Stderr contains regular log lines before/after the marker.
  - Expected: `run-review` parses the marker reliably and ignores unrelated stderr.

- **TC-15: Malformed marker fallback**
  - Type: unit
  - Input: Stderr contains an incomplete or malformed marker.
  - Expected: Wrapper does not crash; failure falls back to subprocess/provider unknown classification with a useful reason.

- **TC-16: next-action reads reviewStop**
  - Type: integration
  - Input: `flow.json` has active stopped review step with `reviewStop`.
  - Expected: `flow get next-action` returns `stopReason`, `classification`, `retryBudgetConsumed`, and `recoveryCommand`.

- **TC-17: next-action reads reviewRetry metrics fallback**
  - Type: integration
  - Input: `flow.json` lacks `reviewStop` but contains reviewRetry metrics describing stop state.
  - Expected: `flow get next-action` returns equivalent stop fields from metrics.

- **TC-18: next-action precedence**
  - Type: unit
  - Input: Both `reviewStop` and reviewRetry metrics exist with differing values.
  - Expected: Defined precedence is followed consistently, preferably `reviewStop` as authoritative.

- **TC-19: status summarizes stopped active review**
  - Type: acceptance
  - Input: Active review step is stopped due to provider failure.
  - Expected: `flow get status` displays stop reason and next recovery operation including recovery command.

- **TC-20: status summarizes input size recovery**
  - Type: acceptance
  - Input: Active review step is stopped due to input size failure.
  - Expected: Status clearly explains input-size classification and shows the recovery operation without suggesting automatic retry.

- **TC-21: status for non-stopped review remains unchanged**
  - Type: acceptance
  - Input: Active review step is running or completed without stop state.
  - Expected: No stopped-review summary is shown; existing status output remains stable.

- **TC-22: Task-scope soft limit is distinguishable**
  - Type: acceptance
  - Input: Task-scope review reaches next-action maxAttempts currently equal to 1.
  - Expected: Prompt or CLI-facing status indicates this is a task-scope soft limit and distinguishes it from flow-scope review enforcement.

- **TC-23: Flow-scope enforcement remains hard stop**
  - Type: acceptance
  - Input: Flow-scope review exceeds allowed attempts.
  - Expected: CLI shows hard enforcement / maxAttempts exceeded behavior, not the task-scope soft-limit wording.

- **TC-24: Issue-log policy is documented**
  - Type: unit
  - Input: Inspect CLI-facing docs or policy text.
  - Expected: Policy states provider/input size failures are not always logged; issue-log is required for workaround, spec decision, or unresolved manual recovery.

- **TC-25: Provider failure does not automatically create issue-log**
  - Type: integration
  - Input: Provider failure occurs with clear automatic recovery command and no workaround/spec decision/manual unresolved recovery.
  - Expected: No issue-log entry is created solely because of the provider failure.

- **TC-26: Input size failure with workaround creates issue-log**
  - Type: integration
  - Input: Input size failure requires a workaround or manual recovery.
  - Expected: Issue-log entry is created with classification, reason, and recovery context.

- **TC-27: Recovery command is actionable**
  - Type: unit
  - Input: Generated envelopes for provider failure, input size failure, and maxAttempts exceeded.
  - Expected: `recoveryCommand` is non-empty, CLI-facing, and specific enough to run or display.

- **TC-28: Missing recovery fields fail validation**
  - Type: unit
  - Input: Attempt to create failure envelope without `classification`, `reason`, `recoveryHint`, or `recoveryCommand` where required.
  - Expected: Constructor/helper rejects or test detects invalid envelope shape.

- **TC-29: Retry budget boundary for provider/input failures**
  - Type: integration
  - Input: Existing reviewRetry count is near max; provider failure occurs.
  - Expected: Count remains unchanged; next-action/status report `retryBudgetConsumed=false`.

- **TC-30: End-to-end stopped review recovery display**
  - Type: acceptance
  - Input: Run flow review, force provider failure, then run `flow get next-action` and `flow get status`.
  - Expected: Both commands consistently show same classification, stop reason, retry budget state, and recovery command.

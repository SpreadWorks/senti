# Draft: Container 初期化時の config フォールバックを null に変更

**開発種別:** enhancement (refactor)

**目的:** Container 初期化時に config 欠落を空オブジェクトで握りつぶさず、欠落を明示的に表現し、config を必要とするコマンドが config なしで黙って動作する状態を排除する。config 必須チェックを共通の前処理層で一元化する。

**Related issue:** #175

## 背景

現状、Container 初期化時に config ロードが失敗すると空オブジェクトが register される。このため config を参照する後段のコードが空 config のまま動作し、エラーが遅延・潜在化する。明示的な未設定チェックは一部のコマンドにしか存在せず、他コマンドは黙って進む。

Issue 1877 指摘 11（エラーハンドリングの不統一）の残存点として 2026-04-18 のレビューで発見された。

## Discussion mode

**本 Q&A は brainstorm ではなく decision モードである。** 各 Q に対する A は確定した方針であり、代替案セクションの却下判断もすべて確定結果として記載している。

## Q&A

### Q1: 提案されたアプローチで進めてよいか？

**A:** はい。「config 欠落時は欠落を明示する値を register する」「config 必須チェックを共通前処理層で統一する」の 2 点を実施する。
*根拠:* (1) 既存コードパターン — Container 初期化処理は既に内部で config ロード成否を追跡しており、この情報を container 登録値のセマンティクスに反映させるのが自然な拡張である。(2) 既存コードパターン — CLI には全コマンドの共通前処理を担う集約点が存在し、前提条件チェックを追加する自然な場所となる。(3) Issue #175 proposal の方向性とも合致。

### Q2: config 欠落の表現方法は？

**A:** 欠落を明示する専用値を register する（未登録状態と区別でき、かつ空オブジェクトと区別できる値）。
*根拠:* (1) 既存コードパターン — 後段消費者は config 参照時に既に欠落値を受容する設計になっている。空オブジェクトと欠落を区別するため、未登録でも空オブジェクトでもない明示値が必要。(2) guardrail「OOP による型表現」（プロジェクト CLAUDE.md）— 値のセマンティクスを型で表現する方針と整合。

### Q3: config 必須チェックをどこで行うか？

**A:** コマンドの共通前処理層で一元的に行う。
*根拠:* (1) 既存コードパターン — 共通前処理層は全コマンドが通る唯一の集約点であり、前提条件チェックの追加先として一貫。(2) guardrail「シンプルなインターフェースに十分な実装を隠す」（プロジェクト CLAUDE.md）— 各コマンドに散らばったチェックより、共通の深いモジュールにチェックを持たせる方が望ましい。

### Q4: どのコマンドが config を必要とするか？

**A:** config を読む全コマンド。config 不要コマンドは `setup`（config を生成する側）、`help`、`upgrade`、`presets`。宣言方式は「必要なコマンドで明示的に宣言する」方向とし、デフォルトは不要扱い。
*根拠:* (1) 既存コードパターン — Container 初期化のコメントにも「setup 未実行の help 等は config 不要」と明記、(2) 既存コードパターン — 各コマンドの属性を集約する共通の登録箇所が存在し、そこに宣言を追加する形で整合する。

### Q5: 既存の後段消費者は欠落表現に対応可能か？

**A:** Agent / ProviderRegistry / Logger / paths いずれも既に欠落値を受容する設計。追加の防御コードは不要。
*根拠:* (1) 既存コードパターン — 後段コードは config 参照時に欠落値を吸収する仕組みを備えている、(2) guardrail「過剰な防御コードを書かない」（プロジェクト CLAUDE.md）。

### Q6: 既存の防御フォールバック（コマンド内で「欠落なら空オブジェクト」とみなす処理）はどうするか？

**A:** 共通前処理層での必須チェックが先行するため削除する。
*根拠:* (1) guardrail — alpha 版ポリシー「後方互換コードは書かない」、防御コード抑制（プロジェクト CLAUDE.md）、(2) 既存コードパターン — 共通層が前提条件を保証する以上、重複防御は不要。

### Q7: 挙動変化と migration plan

**A:** 既存ユーザーから見た挙動変化は 1 点:

- setup 未実行状態で config 必須コマンドを実行した場合、従来は後段での不定エラーまたは silent failure だったが、**実行開始直後に未設定エラーで即座に失敗**するようになる。

**Migration plan:**

- エラーメッセージは既存の未設定エラーと同一文言（`config.json not found. Run sdd-forge setup first.`）を採用し、ユーザー対応手順を明示する。
- CLI のコマンド名・オプション名・引数は一切変更しない。
- config 不要コマンドの動作は完全に同一。
- alpha 版のため deprecation 期間は設けない。既存挙動は silent failure であり、早期失敗化は互換破壊ではなく改善と位置付ける。
*根拠:* (1) guardrail「Backward-Compatible CLI Interface」— CLI 構文を維持、(2) guardrail「alpha 版ポリシー」（プロジェクト CLAUDE.md）— deprecation 期間は不要。

### Q8: Test strategy

**A:** 契約レベルのテストを追加する。具体的な配置とテスト内容は test phase で決定する。

- Container 初期化の config 欠落時の振る舞い
- config 必須コマンドの欠落時失敗挙動
- config 不要コマンドの欠落時正常動作

*根拠:* 既存コードパターン — `tests/` 配下の formal tests は契約レベルの挙動を検証しており、本変更も同様の契約を対象とする。

### Q9: 代替案

**A:**

1. **現状維持**: 却下。型セマンティクスが緩くバグ発見が遅れる。
2. **各コマンドでローカルチェックを追加**: 却下。重複が増え「統一」目標に反する。guardrail「シンプルなインターフェースに十分な実装を隠す」に反する。
3. **欠落の明示 + 一元チェック（採用）**: Issue proposal と guardrail 双方に合致。

### Q10: Future extensibility

**A:** 同じパターンで他の前提条件（active flow 必須等）を共通メタデータとして追加できる。共通前処理層での統一的な前提条件ハンドリング基盤を提供する第一歩となる。

## Requirements（優先順）

### P1 (MUST)

**R1.** Container 初期化後、config が利用不可能な場合は container に登録される config 値が、空オブジェクトでなく、かつ未登録でもない「欠落を示す専用値」であること。利用可能な場合は読み込んだ config オブジェクトそのものであること。
*トリガ:* `sdd-forge <cmd>` 実行時に config が存在しない、または読み込みに失敗した場合
*期待挙動:* container から取得した config 値は空オブジェクトではなく欠落を示す値である。有効な場合は config オブジェクトそのものが返る。呼び出し側は簡潔な等価比較（欠落値との比較）で欠落を判定できる

**R2.** config を必須として宣言したコマンドを config 欠落状態で実行したとき、コマンドの業務処理に入る前に停止し、既存の未設定エラーと同一コード (`NO_CONFIG`) と同一メッセージ (`config.json not found. Run sdd-forge setup first.`) で失敗すること。
*トリガ:* config 必須宣言を持つコマンドを config 欠落状態で実行した場合
*期待挙動:* コマンドの業務処理が 1 行も実行されないままエラー終了する

**R3.** config を必要とする各コマンドは、その必要性を宣言するフラグを持てること。config 不要なコマンド (`setup`, `help`, `upgrade`, `presets`) はフラグを持たないこと。
*トリガ:* 実装時および将来のコマンド追加時
*期待挙動:* config 必要性を宣言したコマンドと宣言していないコマンドの境界が明確であり、宣言を grep 等で一括取得できる

### P2 (SHOULD)

**R4.** 未設定エラー (`NO_CONFIG`) を生成する経路は 1 箇所の共通前処理層に集約され、複数コマンドファイルに重複した局所チェックが存在しないこと。
*トリガ:* リファクタ実施時
*期待挙動:* `NO_CONFIG` を返すコードパスが 1 箇所のみ

**R5.** コマンド本体のコードに、config 欠落時の防御的フォールバック（欠落時に空オブジェクトや暫定値を代用する処理、例: `container.get("config") || {}`）が存在しないこと。
*トリガ:* リファクタ実施時
*期待挙動:* コマンド本体は config が常に有効であることを前提に記述される

### P3 (MUST for correctness)

**R6.** config 不要コマンド (`setup`, `help`, `upgrade`, `presets`) は config 欠落状態でも本変更前と同一の出力・同一の終了コードで動作すること。
*トリガ:* config 欠落状態で config 不要コマンドを実行した場合
*期待挙動:* `NO_CONFIG` を返さず、正常に処理を完了する

**R7.** CLI の外部インターフェース（コマンド名・引数・オプション）は変更しないこと。
*トリガ:* 本 spec の実装
*期待挙動:* 既存のコマンド呼び出しがそのまま動作する（失敗タイミングと形式は R2 に従い変化するが、呼び出し側の構文には影響しない）

## Acceptance Criteria

1. config 欠落状態で container から config を取得したとき、空オブジェクトではなく欠落を示す値が返り、呼び出し側から等価比較で欠落を判定できる (R1)
2. config 必須コマンドを config 欠落状態で実行すると、`NO_CONFIG` コードと既存文言で即座に失敗する (R2)
3. config 不要コマンド (`setup`, `help`, `upgrade`, `presets`) は config 欠落状態で本変更前と同一の動作をする (R6)
4. 追加したテストと既存テスト (`npm test`) の両方がパスする（regression なし）

## Impact on Existing Features

- setup 未実行状態で config 必須コマンドを叩いた際の失敗タイミングが早まり、silent failure が解消される。
- 他の既存機能（docs 生成パイプライン、flow 遷移、spec gate 等）の挙動変化はない。
- ユーザー向けのエラーメッセージ文言は既存の未設定エラーを流用し、対応手順を維持する。

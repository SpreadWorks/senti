# Draft: 221-persist-user-approval

**開発種別:** bugfix
**目的:** spec 承認状態を spec.json で永続化することで、`spec render` による spec.md 再生成時に承認情報（`[x]` チェックと confirmation 日時）が消失しないようにする。

## Scope Verification
- In scope:
  - **[must]** When `spec render` runs, the renderer shall produce the `## User Confirmation` section from a persisted approval data field on spec.json (rather than a hand-written marker on spec.md), so that re-rendering shall not silently revert the approval state.
  - **[must]** When the user approves a spec via the SDD flow approval step, the approval state (approved flag, confirmation timestamp, optional notes) shall be written to spec.json and shall survive subsequent `spec render` runs.
  - **[must]** If spec.json has no persisted approval data (e.g., new specs prior to approval), the renderer shall output an unapproved `## User Confirmation` placeholder so that the existing gate validation continues to pass.
  - **[should]** Documentation and skill instructions for the approval step shall reference the new persistence path so that the next reader does not re-introduce the manual edit pattern.
- Out of scope:
  - Per-task spec approval persistence (per-task spec files are not regenerated by `spec render` and therefore do not exhibit this bug).
  - Migration of historical spec.json files (alpha policy: no backwards-compatibility shims; pre-existing specs shall surface as unapproved on first re-render).
  - "Section preservation" alternative (Option B in the issue): rejected in favor of the data-driven Option A.
  - An explicit "unapprove" / withdraw operation (deferrable until a real need arises).

## Impact on Existing Features
- 影響ありの既存機能:
  - `sdd-forge spec render` — Output of `## User Confirmation` becomes data-driven; previous hand-edited content on spec.md will no longer round-trip.
  - SDD flow approval step (skill `sdd-forge.flow`, plan-level approval) — Operator action shifts from editing spec.md to invoking a CLI to persist approval state.
  - `sdd-forge flow run gate` — Continues to require the `## User Confirmation` section to exist; behavior shall remain compatible because the renderer always emits the section.
- 影響なし:
  - draft.md `## User Approval` — draft is generated once and not re-rendered; not subject to this bug.
  - Per-task spec `## User Confirmation` — task spec files are authored manually, not regenerated.
  - All other `spec render` sections (Goal, Scope, Requirements, etc.) — unchanged.

## Q&A
- Q: Why Option A (data-driven persistence) instead of Option B (preserve existing spec.md section)?
  - A: A is the recommended approach from the issue. It is data-driven, more auditable, and aligns with spec 220's design principle of "reading statically from flow state". B requires read-modify-write parsing on every render and risks subtle regressions across spec.md formatting changes.
- Q: Should the persisted approval be a required schema field?
  - A: No. Required would prevent freshly created specs (which exist before approval) from passing schema validation. Optional with an "unapproved" default at render time preserves the existing lifecycle.
- Q: What format for the confirmation timestamp?
  - A: ISO 8601 string. When the operator does not supply one, the approval CLI shall default to the current time at the moment of invocation.
- Q: How should withdrawing an approval work?
  - A: Out of scope for this bugfix per alpha policy; introduce only when a concrete need is identified.

## Background

When the number of files in the diff reaches `LOOP_REVIEW_THRESHOLD=10` or more, impl-review enters loop review and groups diff chunks into up to `MAX_LOOP_CALLS=16` chunks before calling the AI review provider.

The current `runLoopReviewWithDependencies` only avoids duplicate calls for the same chunk input hash within the same process using an in-process `Map seen`; it has no checkpoint / resume mechanism across processes. If the entire review is interrupted by a provider failure / timeout / parser failure / schema failure while executing a chunk, successfully completed chunks cannot be reused as structured artifacts.

`runImplReview` and `writeReviewAttemptHistory` write `review.md` / `impl-review.json` / `review-history/impl-attempt-*.json` after review output has been obtained. Therefore, when loop review fails midway, the success/failure state, target files, input hash, provider identity, and retry count for each chunk are not preserved.

`.senti/agent-cache` may be usable for reusing responses for exact prompt/provider matches, but it is not a resume mechanism for managing WorkUnit success/failure state, target diffs, aggregation state, or units that need to be rerun.

## Goal

Add a small shared foundation that can checkpoint / resume WorkUnits at the granularity of AI calls, and as the initial application, make impl-review loop review resumable after partial failure.

Even if a long impl-review fails midway, the next run should reuse successful WorkUnits and execute only failed or unexecuted WorkUnits. The canonical final outputs remain `impl-review.json` and `review.md`; chunk artifacts are intermediate checkpoints used to generate those outputs.

## Scope

### In scope

- impl-review loop review chunk calls
- loop review cross-check calls
- WorkUnit identity / checkpoint artifact / resume decision / retry count
- skipping successful WorkUnits
- rerunning failed or stale WorkUnits
- generating `impl-review.json` / `review.md` after all WorkUnits succeed
- generalizing configuration for excluded review target paths

### Out of scope

- changing single-shot impl-review behavior
- applying WorkUnits to impl-gate / integration gate
- applying WorkUnits to test-review / draft-review / spec-review
- changing the `.senti/agent-cache` specification
- changing the semantic retry budget specification for review findings
- changing the initial splitting policy for `LOOP_REVIEW_THRESHOLD` / `MAX_LOOP_CALLS`

Expansion to gate batch and similar areas will not be implemented in this spec. That should be a separate enhancement after the API introduced here has stabilized in impl-review.

## Specification

### WorkUnit foundation

A WorkUnit represents a rerunnable unit corresponding to one AI provider call. Its value structure should be represented by a dedicated class, not by an object literal or a pseudo discriminated union.

WorkUnit identity is calculated from at least the following:

- phase: `impl-review`
- kind: `loop-chunk` or `loop-cross-check`
- stable order key: chunk index or cross-check
- target files: list of normalized target file paths
- input hash: hash of the input equivalent to the user prompt passed to the provider
- commandId: `flow.impl.review.propose`
- provider identity: resolved provider/profile/model-equivalent values
- prompt version
- schema version

Existing artifacts whose identity does not match are treated as stale and are not reused, even if they were successful.

### Checkpoint artifact

Checkpoints are saved under the spec directory. To avoid conflicts with existing attempt history, use the following dedicated area:

`review-history/work-units/impl-review/<unit-id>.json`

Artifacts contain at least the following:

- version
- phase
- kind
- unitId
- identity
- targetFiles
- inputHash
- provider identity
- promptVersion
- schemaVersion
- status: `success` / `failed` / `skipped`
- attemptCount
- startedAt / finishedAt
- rawResponse, on success
- parsedProposals or parsedFindings, on success
- failureKind / failureReason, on failure
- retryable, on failure
- parentUnitId, when the WorkUnit is a child generated by fallback splitting

`rawResponse` and failure details are treated as development evidence under the spec directory, like existing artifacts. Do not add functionality that newly collects secret information.

### Resume rules

1. Before running loop review, determine the WorkUnit plan required for the current run.
2. If a checkpoint has `success` and the WorkUnit identity matches exactly, reuse it without calling the provider.
3. If there is no checkpoint, the checkpoint is `failed`, or the identity does not match, execute the WorkUnit.
4. On successful execution, immediately save a `success` checkpoint.
5. For provider failure / timeout / parser failure / schema failure, immediately save a `failed` checkpoint and stop that run as a tooling failure.
6. On the next run, skip successful WorkUnits and resume from failed or unexecuted WorkUnits.
7. Run the aggregator and generate `impl-review.json` and `review.md` only when all WorkUnits are `success`.

A tooling failure is not a semantic review finding, so it must not consume the semantic retry budget for reviewRetry.

### Aggregator

Loop review chunk results are combined in the original WorkUnit plan order.

The current loop review converts the proposal list to `nonBlockingImprovements` through `loopProposalsToImplReviewJson`. The initial implementation in this specification should preserve the same semantics, and loop chunk proposals must not be promoted to blocking findings.

Preserve the current condition for cross-check: run it when there are at least two chunk summaries and there is remaining capacity under `MAX_LOOP_CALLS`. The cross-check itself is also checkpointed as a WorkUnit. The cross-check identity is calculated from the list of hashes for the chunk summaries included in its input.

### Fallback splitting

If the same `loop-chunk` WorkUnit fails twice with a retryable tooling failure, split only that WorkUnit into child WorkUnits and rerun it.

- Each child WorkUnit processes one group within the parent chunk.
- Each child WorkUnit has `parentUnitId`.
- Do not create a success checkpoint for the parent WorkUnit; the aggregator expands the successful child results at the parent position.
- Apply fallback splitting only to the failed chunk. Do not change the initial overall chunking or `MAX_LOOP_CALLS`.

### Excluded paths

Keep the existing `REVIEW_EXCLUDE_PATHS` as default exclusions.

Additionally, allow impl-review exclusion globs to be read from config. The setting name is `flow.review.excludePaths`, so project-local large generated artifacts or temporary outputs can be excluded via `.senti/config.local.json`.

Apply exclusions before touched file counting, per-file diff collection, and loop review chunk creation. Do not add project-specific fixed paths under `src/`.

## Acceptance criteria

- Each loop review chunk is immediately saved as a WorkUnit checkpoint.
- If a later chunk has a tooling failure after a chunk has succeeded, the next impl-review reuses the successful chunk without a provider call.
- Only failed / stale / missing WorkUnits are rerun.
- Before all WorkUnits succeed, `impl-review.json` / `review.md` are not generated as successful artifacts.
- After all WorkUnits succeed, `impl-review.json` / `review.md` are generated with the same decision semantics as today.
- Loop proposals continue to be treated as `nonBlockingImprovements` and are not promoted to a blocking verdict.
- Cross-check is also saved and reused as a WorkUnit.
- After the same chunk has two retryable failures, only that chunk is split into group-level child WorkUnits.
- Provider failure / timeout / parser failure / schema failure are treated as tooling failures and do not increment semantic reviewRetry.
- Globs specified in `flow.review.excludePaths` are excluded from impl-review targets.
- Default exclusions and exclusions from local config use the same decision logic for both fallback diff and loop review.
- The new implementation uses only Node.js built-in modules.
- New value structures are represented by dedicated classes.

## Test considerations

- WorkUnit identity changes when input hash / provider identity / prompt version / schema version differ.
- A success checkpoint is reused only when identity matches.
- Only WorkUnits with failed checkpoints are rerun.
- When a chunk fails midway, successful checkpoints remain and final artifacts are not generated.
- On rerun, successful checkpoints are used and final artifacts are generated.
- Cross-check WorkUnits are saved and reused.
- After the same chunk fails twice, fallback splitting into child WorkUnits occurs.
- `flow.review.excludePaths` affects touched file count and per-file diff collection.
- Tooling failures do not increment reviewRetry.

## Implementation notes

Do not make the existing `runLoopReviewWithDependencies` overly large; separate WorkUnit planning / storage / running / aggregation. Keep phase-specific chunk creation, prompt creation, response parsing, artifact aggregation, and verdict decision logic on the impl-review side.

Limit the shared foundation to the checkpoint / resume primitives needed by impl-review. Do not introduce abstractions that depend on gate batch or other review phases in this spec.

## 背景

impl-review は差分対象ファイル数が `LOOP_REVIEW_THRESHOLD=10` 以上になると loop review に入り、差分 group を最大 `MAX_LOOP_CALLS=16` の chunk にまとめて AI review provider を呼び出す。

現状の `runLoopReviewWithDependencies` は、同一プロセス内の `Map seen` で同一 chunk input hash の重複呼び出しを避けるだけで、プロセスをまたいだ checkpoint / resume は持たない。chunk 実行中の provider failure / timeout / parser failure / schema failure で review 全体が中断すると、成功済み chunk は構造化 artifact として再利用できない。

`runImplReview` と `writeReviewAttemptHistory` は review output が得られた後に `review.md` / `impl-review.json` / `review-history/impl-attempt-*.json` を書く。したがって loop review の途中失敗では、chunk 単位の成功・失敗・対象ファイル・入力 hash・provider identity・retry count が残らない。

`.senti/agent-cache` は完全一致 prompt/provider の応答再利用に使える可能性はあるが、WorkUnit の成功/失敗状態、対象 diff、集約状態、再実行対象を管理する resume 機構ではない。

## 目的

AI 呼び出し単位の WorkUnit を checkpoint / resume できる小さな共通基盤を追加し、初期適用として impl-review の loop review を途中再開可能にする。

長い impl-review が途中失敗しても、次回実行では成功済み WorkUnit を再利用し、失敗または未実行の WorkUnit だけを実行する。最終出力の正本は引き続き `impl-review.json` と `review.md` とし、chunk artifact はそれらを生成するための中間 checkpoint とする。

- loop review の cross-check 呼び出し
- WorkUnit identity / checkpoint artifact / resume 判定 / retry count
- 成功済み WorkUnit の skip
- 失敗または stale な WorkUnit の再実行
- 全 WorkUnit 成功後の `impl-review.json` / `review.md` 生成
- review 対象除外パスの汎用設定化

### 対象にしない

- single-shot impl-review の挙動変更

## 仕様

### WorkUnit 基盤

WorkUnit は「1 回の AI provider 呼び出しとして再実行可能な単位」を表す。値の構造は専用 class で表現し、object literal / discriminated union もどきにはしない。

WorkUnit identity は少なくとも以下から計算する。

- phase: `impl-review`
- kind: `loop-chunk` または `loop-cross-check`
- stable order key: chunk index または cross-check
- target files: 対象ファイルの正規化済み path 一覧
- input hash: provider に渡す user prompt 相当の入力 hash
- commandId: `flow.impl.review.propose`
- provider identity: 解決済み provider/profile/model 相当の値
- prompt version
- schema version

identity が一致しない既存 artifact は stale として扱い、成功済みでも再利用しない。

### Checkpoint artifact

checkpoint は spec directory 配下に保存する。既存の attempt history と衝突しないよう、以下の専用領域を使う。

`review-history/work-units/impl-review/<unit-id>.json`

artifact は少なくとも以下を持つ。

- version
- phase
- kind
- unitId
- identity
- targetFiles
- inputHash
- provider identity
- promptVersion
- schemaVersion
- status: `success` / `failed` / `skipped`
- attemptCount
- startedAt / finishedAt
- rawResponse（成功時）
- parsedProposals または parsedFindings（成功時）
- failureKind / failureReason（失敗時）
- retryable（失敗時）
- parentUnitId（fallback 分割で生成された子 WorkUnit の場合）

`rawResponse` と failure detail は、既存 artifact と同じく spec 配下の開発用 evidence として扱う。秘密情報を新たに収集する機能は追加しない。

### Resume ルール

1. loop review 実行前に、今回必要な WorkUnit plan を決定する。
2. checkpoint に `success` があり、identity が完全一致する WorkUnit は provider を呼ばずに再利用する。
3. checkpoint がない、`failed`、または identity 不一致の WorkUnit は実行する。
4. 実行成功時は `success` checkpoint を即時保存する。
5. provider failure / timeout / parser failure / schema failure は `failed` checkpoint を即時保存して、その run は tooling failure として停止する。
6. 次回実行では成功済み WorkUnit を skip し、失敗または未実行 WorkUnit から再開する。
7. 全 WorkUnit が `success` になった場合だけ aggregator を実行し、`impl-review.json` と `review.md` を生成する。

tooling failure は semantic review finding ではないため、reviewRetry の semantic retry budget を消費しない。

### Aggregator

loop review の chunk 結果は元の WorkUnit plan 順で合成する。

現行の loop review は proposal list を `loopProposalsToImplReviewJson` で `nonBlockingImprovements` に変換している。この仕様では初期実装も同じ意味付けを維持し、loop chunk の proposal は blocking finding に昇格しない。

cross-check は、chunk summary が 2 件以上あり、`MAX_LOOP_CALLS` の余力がある場合に実行する現行条件を維持する。cross-check 自体も WorkUnit として checkpoint する。cross-check の identity は、入力に含める chunk summary の hash 一覧から計算する。

### Fallback 分割

同じ `loop-chunk` WorkUnit が retryable な tooling failure で 2 回失敗した場合、その WorkUnit だけを子 WorkUnit に分割して再実行する。

- 子 WorkUnit は親 chunk 内の group を 1 group ずつ処理する。
- 子 WorkUnit は `parentUnitId` を持つ。
- 親 WorkUnit の成功 checkpoint は作らず、aggregator は子 WorkUnit の成功結果を親の位置に展開して扱う。
- fallback 分割は失敗した chunk にだけ適用し、初回の全体 chunking と `MAX_LOOP_CALLS` は変更しない。

### 除外パス

既存の `REVIEW_EXCLUDE_PATHS` はデフォルト除外として維持する。

追加で、config から impl-review 用の除外 glob を読めるようにする。設定名は `flow.review.excludePaths` とし、`.senti/config.local.json` でプロジェクトローカルな巨大生成物や一時出力を除外できるようにする。

除外は touched files count、per-file diff 収集、loop review chunk 作成の前に適用する。`src/` には特定プロジェクト固有の path を固定値として追加しない。

## 受け入れ条件

- loop review の各 chunk が WorkUnit checkpoint として即時保存される。
- chunk 成功後に後続 chunk が tooling failure した場合、次回の impl-review は成功済み chunk を provider 呼び出しなしで再利用する。
- failed / stale / missing の WorkUnit だけが再実行される。
- 全 WorkUnit 成功前は `impl-review.json` / `review.md` を成功 artifact として生成しない。
- 全 WorkUnit 成功後は現行と同じ判定意味で `impl-review.json` / `review.md` を生成する。
- loop proposal は引き続き `nonBlockingImprovements` として扱われ、blocking verdict に昇格しない。
- cross-check も WorkUnit として保存・再利用される。
- retryable な同一 chunk failure 2 回後、その chunk だけが group 単位の子 WorkUnit に分割される。
- provider failure / timeout / parser failure / schema failure は tooling failure として扱われ、semantic reviewRetry を増やさない。
- `flow.review.excludePaths` に指定した glob は impl-review 対象から除外される。
- デフォルト除外と local config 由来の除外は、fallback diff と loop review の両方で同じ判定になる。
- 新しい実装は Node.js 組み込みモジュールだけで実現する。
- 新しい値構造は専用 class で表現する。

## テスト観点

- WorkUnit identity が input hash / provider identity / prompt version / schema version の差分で変わること。
- success checkpoint が identity 一致時だけ reuse されること。
- failed checkpoint がある WorkUnit だけ再実行されること。
- chunk 途中失敗時に成功済み checkpoint が残り、最終 artifact は生成されないこと。
- 再実行時に成功済み checkpoint を使って最終 artifact が生成されること。
- cross-check WorkUnit が保存・再利用されること。
- 同一 chunk 2 回失敗後に子 WorkUnit へ fallback 分割されること。
- `flow.review.excludePaths` が touched files count と per-file diff 収集に効くこと。
- tooling failure が reviewRetry を増やさないこと。

## 実装メモ

既存の `runLoopReviewWithDependencies` を巨大化させず、WorkUnit の plan / store / runner / aggregation を分ける。phase 固有の chunk 作成、prompt 作成、response parser、artifact aggregator、verdict 判定は impl-review 側に残す。

共通基盤は impl-review に必要な checkpoint / resume primitive に限定する。gate batch や他 review phase に依存した抽象化はこの spec では作らない。

## Background

For the run ID transcription error observed in Issue #473, the current skill instructs agents to keep the run ID as an opaque token and build `targetGuardArgs` only once for reuse. In addition, only for read-only `senti flow get status` against the same target, it allows a one-time transcription recovery under strict conditions.

This is a safe interim measure that reduces the frequency of typos, but the normal Flow dispatcher exits with `ACTIVE_FLOW_MISMATCH` when there is a target mismatch. Even now, guards for target-sensitive commands are included in command text assembled by the agent, and are not centrally generated from an immutable binding or structured directive inside the CLI.

## Problem

The validity of Flow continuation depends on skill wording and the agent's string transcription. This design violates the agent-independence requirement, and can reproduce the same unnecessary stop with agents that do not follow the skill, context compaction, or another host.

What is needed is not a one-time retry of writes to an incorrect target. We need to deterministically generate guarded commands from the correct target binding and eliminate the typo path itself. The fail-closed contract of `ACTIVE_FLOW_MISMATCH` should be preserved.

## Approach

- Keep an immutable `FlowTargetBinding` inside the CLI, validated by its constructor against the run ID, Issue, spec, managed worktree / branch authority.
- Structured directives returned by `next-action` / dispatcher generate the target guard from the binding itself. The agent does not reconstruct the run ID or guard arguments.
- Before each side effect, the dispatcher compares the directive's target binding with the current authority, and on mismatch fails closed with `ACTIVE_FLOW_MISMATCH` before the side effect, as before.
- Explicitly mark the existing read-only status transcription recovery as a compatibility path until migration to structured binding, or remove it if it becomes unnecessary.
- Do not introduce behavior that automatically reruns mutating commands after `ACTIVE_FLOW_MISMATCH` due to a typo.
- The skill should only describe the usage contract of executing the directive returned by the CLI as-is; target identity safety should be guaranteed on the CLI side.

## Acceptance Criteria

1. All target-sensitive actions in normal Flow are bound to a single `FlowTargetBinding` generated by the CLI.
2. The agent / skill does not need to re-enter run ID, Issue, or spec strings to assemble guards.
3. Even after context compaction or dispatcher resume, the CLI can reacquire and validate the binding from the active authority.
4. Mismatches in Issue, spec, worktree, branch, or run ID stop before side effects with `ACTIVE_FLOW_MISMATCH`, as before.
5. Commands generated from the correct binding do not cause unnecessary `ACTIVE_FLOW_MISMATCH` due to transcription errors, and can proceed within the same dispatcher invocation.
6. Existing read-only status recovery, no-Issue flows, multiple targets / missing targets, and finalize / cleanup boundaries are verified with focused unit / CLI tests.
7. If the skill source is changed, run `senti upgrade` and update regression tests for the generated skill.

## Out of Scope

- Relaxing or removing target guards
- Automatically rerunning mutating commands after `ACTIVE_FLOW_MISMATCH`
- Automatically adopting targets with different Issue, spec, or worktree
- Changes to direct Flow's state machine or finalize / cleanup safety design

## 背景

Issue #473 で観測した run ID 転記ミスに対し、現行 skill は run ID を opaque token として保持し、`targetGuardArgs` を一度だけ構築して再利用するよう指示している。加えて、同一 target に対する read-only `senti flow get status` に限り、厳密な条件下で一回だけ転記回復できる。

これは誤記の発生頻度を下げる安全な暫定策だが、通常 Flow dispatcher は target mismatch 時に `ACTIVE_FLOW_MISMATCH` で終了する。現在も target-sensitive command の guard は agent が組み立てる command text に含まれており、CLI 内の immutable binding や構造化 directive から一元生成されていない。

## 問題

Flow の継続正当性が skill の文言や agent の文字列転記に依存している。この設計は agent 非依存性の要件に反し、skill を守らない agent、context compaction、別 host では同じ不必要な停止を再発させうる。

必要なのは、誤った target への書き込みを一回再試行することではない。正しい target binding から guarded command を決定的に生成し、誤記経路そのものをなくすことが必要である。`ACTIVE_FLOW_MISMATCH` の fail-closed 契約は維持する。

## 方針

- run ID、Issue、spec、managed worktree / branch authority を constructor で検証する immutable `FlowTargetBinding` を CLI 内に保持する。
- `next-action` / dispatcher が返す構造化 directive は、binding 自身から target guard を生成する。agent は run ID や guard 引数を再構成しない。
- dispatcher は各 side effect 前に directive の target binding と現在の authority を照合し、不一致時は従来どおり副作用前に `ACTIVE_FLOW_MISMATCH` で fail closed する。
- 既存の read-only status 転記回復は、構造化 binding へ移行するまでの互換経路として明示するか、不要になれば削除する。
- mutating command の誤記を `ACTIVE_FLOW_MISMATCH` 後に自動再実行する仕様は導入しない。
- skill は CLI が返す directive をそのまま実行する利用規約のみを記述し、target identity の安全性は CLI 側で担保する。

## 受け入れ条件

1. 通常 Flow のすべての target-sensitive action は、CLI が生成した単一の `FlowTargetBinding` に束縛される。
2. agent / skill が run ID、Issue、spec の文字列を再入力して guard を組み立てる必要がない。
3. context compaction または dispatcher 再開後も、CLI が active authority から binding を再取得・検証できる。
4. Issue、spec、worktree、branch、run ID の不一致は、従来どおり副作用前の `ACTIVE_FLOW_MISMATCH` で停止する。
5. 正しい binding から生成された command は、転記ミスによる不要な `ACTIVE_FLOW_MISMATCH` を起こさず、同一 dispatcher invocation で進行できる。
6. read-only status の既存回復、no-Issue flow、複数 target / target 不在、finalize / cleanup 境界を focused unit / CLI tests で検証する。
7. skill source を変更した場合は `senti upgrade` を実行し、生成済み skill の回帰テストを更新する。

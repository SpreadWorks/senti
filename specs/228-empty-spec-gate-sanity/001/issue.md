## Symptoms

While implementing spec 221, I wrote spec.md first and left spec.json as the empty stub generated by `flow prepare`, then ran `sdd-forge flow run gate --phase spec`. Almost all guardrails passed (some FAILs were due to unrelated reasons).

## Steps to Reproduce

1. Run `sdd-forge flow prepare --title ... --worktree`
2. Leave the generated `specs/<N>/spec.json` as-is (all fields empty: goal="", scope.in=[], requirements=[], etc.)
3. Run `sdd-forge flow run gate --phase spec`

Execution results (excerpt):
- single-responsibility: PASS ("No concerns are specified, so no unrelated changes are bundled.")
- unambiguous-requirements: PASS ("No requirements are present; no vague wording appears.")
- complete-context: PASS ("No requirements are listed, so none violate the When/If + shall pattern.")

## Problem

Multiple guardrails interpret empty arrays / empty strings as "not applicable" and return PASS, allowing a spec with almost nothing written to pass. At minimum, a spec must have non-empty goal / requirements / acceptance_criteria.

## Proposed Fix

Add the following sanity checks at the spec.json level (statically, before AI guardrails):
- `goal` is non-empty
- `requirements` has at least 1 entry
- `acceptance_criteria` has at least 1 entry

If these conditions are not met, return FAIL without invoking AI guardrails.

## Impact

- As in this case, writing spec.md first delays discovery of the issue
- Especially dangerous in auto mode: if an empty spec passes, it causes misalignment in subsequent gate-impl / review steps
- Discovered in spec: 221-worktree-edit-path-guard (spec phase)

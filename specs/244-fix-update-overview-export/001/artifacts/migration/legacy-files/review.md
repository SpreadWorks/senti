Add explicit bounds for overview additions input
**File:** `src/flow/lib/run-update-overview.js`  
**Issue:** The file enforces a size limit for the existing `spec.json` (`MAX_SPEC_JSON_BYTES`) but does not place any explicit upper bound on the incoming `--json` payload, per-key array lengths, or `entry.text` sizes inside `validateOverviewAdditions()`. That leaves bulk user-provided additions effectively unbounded, which conflicts with the `bounded-resource-usage` guardrail and can still produce excessive parsing, merge, render, or write work even when the current `spec.json` is small.  
**Suggestion:** Introduce explicit limits for the request itself, for example `MAX_ADDITIONS_JSON_BYTES`, `MAX_OVERVIEW_ITEMS_PER_KEY`, and `MAX_OVERVIEW_TEXT_LENGTH`, and enforce them during validation before persisting. Also consider rejecting output that would cause the rewritten `spec.json` to exceed the same bounded size policy after merge, not only before reading.

**Verdict:** REJECTED
**Reason:** This is not a refactoring of the actual diff (which only adds `export default RunUpdateOverviewCommand;`); it is a scope-expanding behavior change that introduces new validation thresholds (`MAX_ADDITIONS_JSON_BYTES`, `MAX_OVERVIEW_ITEMS_PER_KEY`, `MAX_OVERVIEW_TEXT_LENGTH`) and new rejection paths. Adding these limits would reject inputs that the current contract accepts, breaking existing behavior, and the specific thresholds are unjustified—any chosen value risks rejecting legitimate AI-emitted additions. The existing `MAX_SPEC_JSON_BYTES` check already bounds the persisted output indirectly via the merged result size if applied post-merge, but that too is a separate design decision. If bounded-resource-usage is genuinely a concern here, it warrants its own spec/issue rather than being bundled into a default-export fix review.
